# 2.0.1 客户端验收清单

**当前没有已完成的 Minecraft 客户端验收记录。下面的复选框故意留空。**

构建、Node 测试、类型检查和可重复打包证明的是代码与资源的内部一致性。Bedrock mock 不模拟区块向客户端传输、光照、红石/AI、JSON UI 引擎、渲染材质或成就系统；不得用自动化通过替代这些结果。

用户已验证“远端自由相机能够显示实体标注”的路线。本轮验收的是这份包的实现，不要求重新证明路线可行。

## 已收到的客户端反馈（2026-10-14）

- 2.0.0：四类标注实体均因 `ponder:alpha` 的 float 默认值被写成整数 `1` 而加载失败。2.0.1 已修正生成器中所有 float 属性的默认值与范围字面量，保留 int/bool 和常量类型，并增加原始 JSON 与内层 mcpack 的回归检查；游戏内复测仍待用户确认。
- 同一日志中的 `realmssettingsscreen.subscriptionlabelformatpreview` 和 `#2025秋季小更新` 不在本包的两份 `.lang` 文件中。片段没有指出这些语言文件属于哪个包，暂不归因于原版或其他特定资源包，也不据此修改它们。

## 3. 时间轴与原生行为

- [ ] 播放、暂停、继续和重播生效，暂停后镜头脚本和说明不再推进。
- [ ] 原生红石、水流、掉落物运动和 AI 不被教学暂停冻结；不将此判为教学时钟故障。
- [ ] 每个关键帧均可点击，暂停时跳转仍保持暂停；播放时跳转仍继续播放。
- [ ] 来回跳转/返回不积累教学实体，不补播过去粒子或重复旧 impulse/event；明确重播可执行起始一次性效果。
- [ ] 舒适阅读开启时，有说明/操作提示的片段按 3:1 放慢，无文本片段正常推进。
- [ ] 场景完成出现“接下来”或“场景已完成”；存在下一场景时高亮对应按钮，不存在时保持禁用。
- [ ] 测试最后一条说明结束、224 像素进度填满、暂停和重开表单等边界，不提前选择完成状态。
- [ ] 在可控低 TPS/网络延迟下记录本地进度动画与服务端教学的差距；点击后重建表单应重新对齐，不出现并发 writer 或恢复后重锁相机。

本地动画不是实时服务端时间传输。低 TPS 时若存在可见不同步，记录偏差与可接受程度，不能把“源码有动画”当成同步验收通过。

## 4. 世界标注与字体

- [ ] 中文、英文、混排、颜色代码、换行均可见；没有字形镜像、倒置、UV 偏移或半个字被裁掉。
- [ ] 匹配生效字体测量后复测窄字、宽字、标点、连续中文和长单词；当前 fallback 字宽不得签为“准确原版字体”。
- [ ] 说明最大宽度、9 单位行距、内外留白与 Java sample 对照，框体随正文尺寸变化。
- [ ] 标注按目标选择左右/上下位置，不是固定右侧三槽；长文本不互相重叠，不盖住关键结构。
- [ ] 运镜过程中框、字、图标朝向相机；指示线连接正确目标，长度、明暗边与粗细一致，无反向线段。
- [ ] through 标注可透视，depth 标注确实受遮挡；alpha 是正常半透明，不把黑底/字形变成实心矩形。
- [ ] 区域轮廓包含完整方块边界；实体轮廓跟随实际包围盒，不大一格、不滞留在初始位置。
- [ ] 使用/攻击/滚动/槽位提示图标、物品贴图和四向小尖角正确；触屏/手柄用通用描述，不出现无效鼠标交互承诺。
- [ ] 远端掉落物、粒子与标注在这份包里正常显示；退出后 owned 实体清理，粒子按其原生寿命消失。

世界文字不需要随 GUI 缩放改变尺寸；验收的是世界布局/镜头是否容纳它，而不是重新引入屏幕尺寸联动方案。

## 6. 多人、维度、容量与性能

- [ ] 在有可用空置候选时，4 名玩家同时进入，播放/暂停/导航互不影响；第 5 名安全拒绝且不清理前 4 名。
- [ ] 主世界、下界、末地分别尝试。只有完整房间和缓冲全为空时才能建造；没有空位应恢复玩家并报告失败，不破坏地形。
- [ ] 一名玩家受伤/退出，其他玩家的相机、输入、时钟和内容不受影响。
- [ ] 存在其他包常加载区时，容量不足不删除它们，也不抢占已有会话。
- [ ] 开发副本中让玩家在建造/清理分批期间靠近展示区；写入应停止，玩家脚下内容不继续被清空，记录保留至安全回收。
- [ ] 大结构、长说明、多标注与 4 人场景记录加载耗时、TPS、帧率、实体数量和退出回收耗时。
- [ ] 检查约 1.5 MiB、1792 个播放预设的生成 UI 在低端设备上的打开耗时和内存；静态大小上限不是性能通过证据。
- [ ] 独立开发副本中触发受控副产物限额，停止会话并恢复玩家；不靠删除访客或玩家实体腾出容量。

超出配置预算应提前校验失败或安全退出，不以强行提高 limits 作为性能验收方案。教学实体在原生行为下的稳定性需要逐种验收，不能从铁锭样例推导所有生物都安全。

## 7. 中断与恢复矩阵

至少在**准备加载、分批建造、正常播放、打开索引、关键帧重建、场景切换、退出回收**这些时机测试：

| 中断 | 预期 |
| --- | --- |
| 受伤 | 正常扣血后立即退出，恢复玩家不等待区块/清理；旧响应不能重开 |
| 死亡与重生 | 关闭会话，重生后恢复原 HUD/输入权限，无残留自由相机 |
| 换维度 | 关闭旧会话，不在错误维度继续渲染或重新锁镜头 |
| 离线与重连 | 无效玩家不强行操作，恢复快照留到再次有效加入 |
| 脚本重载/世界重启 | 恢复玩家，校验完整 journal，再回收本包租约与孤立句柄 |
| 原生 API 暂时失败 | 保留恢复数据，环境恢复后可重试，不先清空 journal |
| 原有部分 HUD/输入已被关闭 | 退出恢复进入前的各项状态，而非一律全开 |

- [ ] 上表各项在目标环境完成，内容日志及世界残留检查无未解释问题。
- [ ] 退出后故意等待迟到表单/加载任务完成，玩家不会再次失去镜头控制。
- [ ] 恢复失败时可见诊断且记录保留；所有活动会话退出、条件安全后允许后台重试。
- [ ] 不同包的自定义相机/HUD 组合另行验收；本包只承诺恢复保存的 HUD/输入并 clear 相机/FOV，不回放另一包相机脚本。

损坏 journal、重复 ID、重叠租约等破坏性故障首先依靠自动化注入测试。不要为了验收直接编辑重要世界的动态属性；需要客户端注入时另用可丢弃副本。
